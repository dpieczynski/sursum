# sursum — plan architektury i pierwszych etapów

## 0. Kontekst

Dwa kościoły parafii wyświetlają teksty pieśni z OpenSong 3.4.8 (Windows → HDMI → przedłużacz HDMI po Ethernecie → projektor / monitor 86"). Problemy: OpenSong nie działa na współczesnym Linuksie, w trybie prezentacji nie da się edytować zestawu bez pokazania pulpitu wiernym, obsługa wymaga klawiatury, a organista ma wolną najwyżej jedną rękę. Cel: lekkie urządzenie (Raspberry Pi 5 przy ekranie) z jedną binarką w Ruście, ekranem jako stroną w kiosku Chromium i pilotem w przeglądarce. Program (to, co widzą wierni) jest oddzielony od edycji zestawu, a podgląd na pilocie jest tym samym komponentem co ekran.

### Decyzje z rozmowy (wiążące dla planu)
| Temat | Decyzja |
|---|---|
| Miejsce Pi | **Przy ekranie/projektorze**, połączone z siecią **Ethernetem**, z opcjonalnym PoE (§11.6). Istniejący kabel przedłużacza HDMI można przerobić na łącze Ethernet/PoE do Pi. |
| MIDI | **Rezygnacja z MIDI.** Wystarczą przyciski na pilocie oraz pedał lub pilot do prezentacji podłączony do tabletu lub PC. |
| Urządzenia pilota | **Tablet z Androidem (Chrome)**, **PC z Linuksem (Chromium/Chrome; preferowany system do testów autora)** i **PC z Windows (Chrome/Edge)**. Firefox na Linuksie: działa, ale test nieblokujący (podgląd nie musi być co do piksela identyczny). iPad: furtka otwarta (nie używamy API niedostępnych w WebKit bez wariantu awaryjnego), ale bez implementacji i testów blokujących. |
| Projekcja w Tulcach | Część obrazu pada na ciemny słup, a tekstu na słupie nie widać. Rozwiązanie programowe: **profil ekranu ze strefami wykluczenia** (§6.6). |
| Sieć | Router lub switch parafii z rezerwacją DHCP; adres Pi w konfiguracji, mDNS (`sursum.local`) jako wygoda. |
| Po restarcie Pi | **Zawsze logo, pozycja zachowana.** Restart samego procesu (serwera lub przeglądarki) w pełni odtwarza ekran. |
| Dotknięcie w pilocie | **Od razu na ekran.** Tryb z podglądem („cue”) to ewentualne późniejsze ustawienie urządzenia; model stanu go przewiduje. |
| Przygotowanie zestawów | Na miejscu przed mszą i ad hoc w trakcie. Priorytety: **łatwy import z OpenSong** i **edytor pieśni obsługiwany klawiaturą**. Szybkie „Pokaż teraz” z wyszukiwarki. |
| Baza pieśni | **Wspólna dla obu kościołów, ręczny eksport/import ze scalaniem** we wczesnym etapie (M3). |

### Stan weryfikacji źródeł
Sprawdzone 2026-11-15 w rejestrach i dokumentacji: wersje crate'ów (sparse index crates.io) i pakietów npm (registry.npmjs.org); Raspberry Pi OS Lite 64-bit z 2026-10-06 na Debianie **Trixie** (os_list Raspberry Pi); `cage` 0.2.0 w Trixie (sources.debian.org); OpenLyrics 0.9 z `<lines break="optional">` (docs.openlyrics.org); podstawowe konwencje OpenSong (opensong.org: spacja na początku linii tekstu, `.` dla akordów, sekcje `[V] [1-9] [C] [B] [P] [T]`, `||` wymusza nowy slajd, w specyfikacji element `<timesig>`); brak oficjalnej nakładki PoE dla Pi 5, są zgodne nakładki firm trzecich.

Równoległe badanie przez agentów przerwał limit użycia, więc te punkty sprawdzamy na początku odpowiednich etapów, a nie przyjmujemy z pamięci.

Środowisko: host to **Aurora-DX (ublue, testing na bazie Fedory 45)**, nie Fedora 44. Ma VS Code (RPM) z Dev Containers, Docker 29.9 i podman 6.1, rustup w `$HOME` (rustc 1.100.0) oraz Node 26 z Homebrew, bez corepacka.

## 1. Architektura w skrócie

```
 Tablet Android (Chrome) ─┐  Wi-Fi/LAN                 Raspberry Pi 5 (przy ekranie)
 PC Linux (Chromium)      ─┤
 PC Windows (Chrome/Edge) ─┼──────── router ── Ethernet(+PoE) ──┐
 (iPad, Firefox: furtka)   ┘                                     │
                                         ┌───────────────────────▼──────────────────┐
                                         │ sursum-server (1 binarka, systemd)       │
                                         │  axum: HTTP API + WS + embedded frontend │
                                         │  StateActor (jedyny właściciel stanu)    │
                                         │  SQLite (WAL) na partycji /data          │
                                         └───────▲──────────────────────────────────┘
                                                 │ ws://localhost (tylko odczyt)
                                         cage + Chromium --kiosk → HDMI-A-1 (wymuszone 1080p60)
```

Zasada: **cała logika jest na serwerze.** Należą do niej parsowanie, podział na slajdy, kolejność, nawigacja, program i podgląd, wyszukiwanie, walidacja edytora oraz wyliczanie obszaru treści ze stref wykluczenia. Przeglądarka wyłącznie rysuje i dobiera rozmiar czcionki.

PC z Linuksem może być pilotem w sieci albo uruchomić całość lokalnie: binarka x86_64-linux, ekran w drugim oknie Chromium w trybie `--kiosk` lub `--app`, pilot na `http://localhost`. To podstawowe środowisko testów autora (§13).

### 1.1 Czytelność kodu (zasada przekrojowa)
Kod ma być czytelny dla człowieka, nawet kosztem drobnej wydajności lub zwięzłości:
- **Czyste funkcje w `sursum-core`**: wejście → wyjście, bez I/O. Takie funkcje łatwo czytać i testować (np. `compile_deck(song, rules) -> Deck`, `content_region(profile) -> Rect`).
- **Małe moduły o jednej odpowiedzialności**, nazwy z dziedziny (`Program`, `Deck`, `ExclusionZone`), a nie techniczne (`Manager`, `Helper`, `Utils`).
- **Jawne typy zamiast „gołych” wartości**: newtypy `SongId`, `ItemId`, `SlideKey`, `Px`; enumy zamiast flag bool.
- **Bez magii**: żadnych własnych makr proceduralnych ani generycznych abstrakcji „na zapas”. Trait tylko tam, gdzie są co najmniej dwie implementacje albo potrzeba wstrzyknięcia w testach (`Platform`, `Clock`).
- **Błędy**: `thiserror` w bibliotekach, `anyhow` tylko w `main` i CLI; komunikaty z kontekstem.
- **Komentarze dokumentacyjne** (`///`) na każdym publicznym typie i funkcji core: *dlaczego*, nie *co*. W `docs/architecture.md` jeden diagram przepływu danych.
- Frontend: komponenty Svelte do ok. 150 linii, logika poza komponentami w zwykłych modułach `.ts`, brak globalnego stanu poza jednym magazynem stanu z WS.
- Narzędzia: `rustfmt`, `clippy` z `-D warnings` (plus wybrane lint'y pedantic, np. `needless_pass_by_value`, `redundant_else`), `prettier`, `eslint`, `svelte-check`; limit złożoności funkcji pilnowany w code review, nie przez narzędzie.

## 3. Model danych

### 3.1 Pieśń (zgodna z OpenLyrics 0.9)
```rust
struct Song {
  id: SongId,                 // UUIDv7, stały przez całe życie (także między urządzeniami)
  revision: u32,              // rośnie przy każdej edycji
  content_hash: Hash,         // sha256 kanonicznego JSON treści (scalanie, deduplikacja)
  titles: Vec<Title>,         // [0] = główny; aka z OpenSong → kolejny tytuł
  authors: Vec<Author>, copyright: Option<String>, ccli: Option<String>,
  songbooks: Vec<SongbookEntry>,   // { songbook_id, entry: "123" } — OpenSong hymn_number
  themes: Vec<String>, keywords: Vec<String>, language: Option<LangTag>,
  verse_order: Vec<VerseName>,     // OpenLyrics verseOrder; puste = kolejność sekcji
  verses: Vec<Verse>,
  notes: Option<String>, source: Provenance,   // np. opensong:<ścieżka>, import_run_id
  extra: BTreeMap<String,String>,  // user1..3, key, capo, tempo, timesig, key_line — bezstratny import
}
struct Verse { name: VerseName /* v1, c, c2, b, p, e, o … */, lang: Option<LangTag>, label: Option<String>, parts: Vec<LinesBlock> }
struct LinesBlock { lines: Vec<Line>, break_after: BreakKind /* Forced (||) | Optional (OpenLyrics) | None */ }
struct Line { text: String, chords: Vec<ChordAt> /* przechowywane, w MVP nie wyświetlane */ }
```
Mapowanie OpenSong → model: `[V1]`→`v1`, `[C]`→`c`, `[B]`→`b`, `[P]`→`p`, `[T]`→`e` (tag/zakończenie) ⚠, nazwy własne → `o<n>` z `label`; `||` → nowy `LinesBlock` z `Forced`; linia `.` → akordy przypięte do kolejnej linii tekstu; `presentation` → `verse_order`. Eksport do OpenLyrics: `Forced` → osobne `<lines>`, `Optional` → `break="optional"`. Niejasności zapisujemy w raporcie importu, a nie zgadujemy po cichu.

### 3.3 Slajdy (wynik kompilatora z core)
```rust
struct Deck { deck_id: Hash /* hash treści i reguł */, fit_group: Hash, item_id: ItemId, slides: Vec<Slide>, background: Background }
struct Slide { key: SlideKey /* np. "c#1@3": sekcja, część, wystąpienie w order */, label: SectionLabel, body: SlideBody }
enum SlideBody { Lyrics { lines: Vec<String> }, Text { title: Option<String>, lines: Vec<String> }, Image { asset_id, fit } }
```
Reguły (`SlideRules` w motywie): maksymalna liczba linii na slajd z dzieleniem po równo, `Forced` zawsze dzieli, `Optional` dzieli tylko powyżej limitu, a sekcja zawsze zaczyna nowy slajd. Klucz slajdu pozwala odnaleźć „ten sam” slajd po edycji pieśni.

Ustawienia połączenia: `journal_mode=WAL`, `synchronous=FULL` (zapisy są rzadkie, więc fsync przy każdym commicie nic nie kosztuje), `foreign_keys=ON`, `busy_timeout=5000`, `trusted_schema=OFF`. Jedno połączenie zapisujące należy do aktora (§4).

Wyszukiwanie **nie używa FTS5**: `unicode61 remove_diacritics` nie składa „ł”, bo U+0142 nie ma rozkładu kanonicznego. Indeks trzymamy w pamięci w `sursum-core::search` (§8).

## 4. Stan serwera, program i podgląd, konflikty

### 4.1 Model współbieżności
- **StateActor**: jedno zadanie (wątek z `blocking_recv`, bo rusqlite jest synchroniczny) jest jedynym właścicielem `AppState { program, active_set, library_index, devices }` i połączenia SQLite.
- Komendy przychodzą przez `mpsc` z `oneshot` na wynik, więc wszystkie zmiany mają **jeden porządek globalny**.
- Rozgłaszanie przez `tokio::sync::watch<Arc<ScreenState>>` i `watch<Arc<RemoteState>>` (semantyka „ostatnia wartość”): wolny klient pomija stany pośrednie i nigdy nie dostaje błędu przepełnienia.
- `rev: u32` rośnie globalnie przy każdej zmianie widocznej dla klientów. Encje (pieśń, zestaw) mają własne `revision`.

### 4.2 Program (to, co widzą wierni) jest zamrożony
```rust
struct Program {
  live: Option<LiveRef { set_id, item_id, deck: Arc<Deck> /* ZAMROŻONA kopia */, slide_index }>,
  ghost: Option<GhostPos>,   // gdy pozycję na żywo usunięto z zestawu: pamiętamy dawny indeks
  overlay: Overlay,          // None | Black | Logo — osobna warstwa, treść pod nią może się zmieniać
  last_actor: ClientId, updated_rev: u32,
}
```
- Przejście na żywo kompiluje `Deck` i kopiuje go do programu. **Edycja zestawu ani pieśni nie zmienia programu.** Ekran dostaje `program.live.deck`, nie dane zestawu.
- „Dalej” i „Wstecz” w obrębie pozycji korzystają z zamrożonego decku. Jeśli pieśń zmieniono w trakcie, przy najbliższej nawigacji deck jest przebudowywany, a pozycja szukana po `SlideKey`; brak klucza → najbliższy slajd tej samej sekcji, ostatecznie przycięcie zakresu.
- Następna i poprzednia pozycja liczone są względem `item_id` w **aktualnym** zestawie. Gdy pozycja na żywo zniknęła, używamy `ghost`: następna = pozycja, która teraz zajmuje dawny indeks.
- **Podgląd** (`preview`) to wyliczany następny slajd: kolejny slajd decku albo pierwszy slajd następnej pozycji (wtedy serwer wysyła też `upcoming: Deck`, żeby ekran mógł wcześniej dopasować czcionkę). Pole `cue: Option<SlidePos>` jest w modelu od razu (w MVP zawsze `None`), więc tryb „najpierw do podglądu” można dodać bez zmiany protokołu.
- Nawigacja przy aktywnej czerni lub logo zmienia treść pod nakładką. Wierni nic nie widzą, a pilot pokazuje, co pojawi się po odsłonięciu.

### 4.3 Rozstrzyganie konfliktów (kilka pilotów)
- **Komendy względne** (`Next`, `Prev`, `NextItem`, `PrevItem`) niosą `base_rev`. Serwer stosuje je, gdy `base_rev == program.updated_rev` **albo** `program.last_actor == ten_klient` (szybkie wielokrotne naciśnięcia jednego operatora działają). W przeciwnym razie odpowiada `Stale`, a pilot krótko sygnalizuje „już przełączone”. Dzięki temu organista i zakrystian naciskający „Dalej” w tej samej chwili nie przeskoczą o dwa slajdy.
- **Komendy bezwzględne** (`GoTo{item_id, slide_key}`, `GoToItemNumber`, `GoToSection`, `SetOverlay`, `ShowNow`) wykonuje się zawsze. Wygrywa ostatni, bo to jawna intencja.
- **Edycja zestawu**: operacje na stabilnych ID (`Add{after}`, `Remove{id}`, `Move{id, before}`) są przemienne w praktyce. Przy brakującym ID odpowiedź `Rejected(NotFound)`, a klient odświeża widok z migawki.
- **Edycja pieśni**: blokada optymistyczna `UpdateSong{id, base_revision, body}`. Przy różnicy rewizji odpowiedź `Conflict` i edytor pokazuje obie wersje. Historia w `song_history` pozwala cofnąć zmianę.

### 4.4 Trwałość programu i polityka startu
- Każda zmiana programu zapisuje `runtime_state` (JSON z `set_id`, `item_id`, `slide_key`, `overlay`, `deck_id`) razem z bieżącym `boot_id`: Linux `/proc/sys/kernel/random/boot_id`, Windows czas startu systemu z `GetTickCount64`.
- Przy starcie serwera:
  - **ten sam `boot_id`** (padł tylko proces) → pełne odtworzenie, także `overlay`;
  - **inny `boot_id`** (odcięcie prądu, restart Pi) → odtworzenie pozycji z `overlay = Logo` (decyzja użytkownika). Przycisk „Pokaż” na pilocie zdejmuje logo jednym dotknięciem.
- Zegar: Pi bez internetu i bez baterii RTC może mieć zły czas. Logika startu nie zależy od zegara (opiera się na `boot_id`). Znaczniki czasu w bazie są informacyjne. Gdy zegar serwera jest wcześniejszy niż data builda, przyjmujemy `client_time` z `Hello` pilota.

## 5. Protokół WebSocket

- Endpointy: `GET /ws/screen` (tylko odczyt, bez autoryzacji, dostęp z pętli zwrotnej i LAN) oraz `GET /ws/remote` (wymaga ciasteczka urządzenia).
- Ramki tekstowe JSON, enumy serde z `#[serde(tag = "t", rename_all = "camelCase")]`.
- REST (`/api/…`) obsługuje rzeczy duże lub na żądanie: wyszukiwanie, szczegóły pieśni, import, eksport, zasoby, parowanie.

**Klient → serwer**
```
Hello   { protocol: u16, role: "screen"|"remote", clientId, buildId, clientTime? }
Cmd     { seq: u32, baseRev: u32, cmd: Command }
Ping    { }
Command = Next | Prev | NextItem | PrevItem
        | GoTo { itemId, slideKey } | GoToItemNumber { n } | GoToSection { label }
        | SetOverlay { overlay: "none"|"black"|"logo" } | ToggleBlack
        | ShowNow { songId }                       // wstaw za bieżącą pozycją i od razu pokaż
        | ActivateSet { setId }
        | SetOp { setId, op: Add{after?, item} | Remove{itemId} | Move{itemId, before?} | UpdateItem{itemId, item} }
```
**Serwer → klient**
```
Welcome   { protocol, buildId, device?, serverTime }
Screen    { rev, live?: { deck: Deck, slideIndex }, upcoming?: Deck, overlay, theme: Theme, transitionMs, logo?: AssetRef,
            layout: ScreenLayout }   // obszar treści i maski wyliczone na serwerze (§6.6)
Remote    { rev, program: ProgramView, preview?: SlideRef, activeSet?: SetView, presence: [DeviceView] }
CmdResult { seq, outcome: Applied{rev} | Stale{rev} | Rejected{code} | Conflict{current} }
Notice    { code, params }          // kody i18n, nie gotowe teksty
Pong      { }
```
- **Migawki zamiast łatek**: każdy stan jest mały (deck ok. 2–5 KB, zestaw poniżej 10 KB), więc wysyłamy całe domeny. Nie ma dziennika zdarzeń, problemów z kolejnością ani logiki łatania. Klient odrzuca wiadomości z `rev` mniejszym niż ostatnio widziany.
- **Ponowne połączenie**: `Hello` → `Welcome` + pełna migawka. Ekran porównuje `deck_id` i `slide_key` z tym, co już ma; jeśli są takie same, **nic nie rysuje ponownie** (żadnego przenikania). Backoff 250 ms → 5 s z losowym rozrzutem, ping co 5 s, brak odpowiedzi przez 15 s oznacza nowe połączenie.
- **Wersje**: `protocol` niezgodny lub `buildId` różny od strony → strona przeładowuje się sama. Ekran robi to tylko wtedy, gdy pokazuje nakładkę albo nic; inaczej czeka do najbliższej zmiany programu. Aktualizacje i tak wgrywamy poza mszą.
- **ts-rs generuje**: `ClientMsg`, `ServerMsg`, `Command`, `SetOp`, `ScreenState`, `RemoteState`, `ProgramView`, `SetView`, `Deck`, `Slide`, `SlideBody`, `Theme`, `Overlay`, `ScreenLayout`, `ScreenProfile`, `Rect`, `CmdOutcome`, `ErrorCode`, `NoticeCode`, DTO REST (`SongSummary`, `SongDetail`, `SearchHit`, `ImportReport`, `MergeReport`, `DeviceView`) oraz `SongMarkupDiagnostics` (diagnostyka edytora).
- **Nie generuje**: wierszy bazy, AST parsera, wewnętrznego `Program`.
- `rev` i liczniki jako `u32`, a dla `u64` jawne `#[ts(type = "number")]` ⚠ (ts-rs mapuje 64-bitowe liczby na `bigint`, do potwierdzenia na docs.rs w M0).
- Eksport wywołuje `just bindings` (`cargo test -p sursum-core --features ts export_bindings` z `TS_RS_EXPORT_DIR=frontend/packages/protocol/src/generated`). CI sprawdza, czy wygenerowane pliki nie różnią się od repozytorium (`git diff --exit-code`).

## 6. Rysowanie ekranu i identyczny podgląd

### 6.1 Strona ekranu
- `<head>` zawiera inline `<style>html,body{margin:0;background:#000;cursor:none;overflow:hidden}</style>` i `<meta name="color-scheme" content="dark">`, a skrypt jest ładowany jako moduł na końcu.
- Żadnych zasobów z sieci. Czcionki WOFF2 z `@fontsource` (subset latin + latin-ext) są wbudowane w binarkę i ładowane z `font-display: block`.
- Brak jakiegokolwiek UI błędów: wyjątki trafiają do `console` i do serwera (`POST /api/screen-log`), nigdy na ekran.

### 6.2 Scena
`Stage` to stały element 1920×1080 skalowany przez `transform: scale(s)` z `transform-origin: 0 0` i wyśrodkowany, gdzie `s = min(vw/1920, vh/1080)`. Na Pi z wymuszonym 1080p `s = 1`. Obszar bezpieczny (marginesy w % per urządzenie, domyślnie 5%) można kalibrować wzorcem testowym z panelu administratora (wyłącznie poza mszą, z potwierdzeniem).

### 6.3 Warstwy (`LayeredStage`)
```
[overlay]  czerń / logo  (własne przenikanie, zawsze na wierzchu)
[layer B]  ─┐ dwie warstwy treści, każda z NIEPRZEZROCZYSTYM tłem (kolor/obraz motywu)
[layer A]  ─┘
```
Zmiana slajdu przebiega tak:
1. Narysuj nowy slajd w ukrytej warstwie (`opacity: 0`).
2. `await document.fonts.ready`, `await img.decode()` dla obrazów i dopasowanie czcionki z pamięci podręcznej.
3. `incoming.animate([{opacity:0},{opacity:1}], {duration: transitionMs, fill:'forwards'})`. Warstwa wychodząca pozostaje nieprzezroczysta pod spodem, dlatego nie ma spadku jasności i nie ma podwójnego tekstu, bo tło przychodzącej warstwy przykrywa starą treść.
4. Po `finished` ukryj starą warstwę i zamień role.

Jeśli w trakcie przenikania przyjdzie nowy stan, wołamy `animation.finish()` (natychmiastowy koniec) i rysujemy tylko najnowszy stan. Przy `transitionMs = 0` zamiana jest natychmiastowa. Licznik `window.__sursum.transitions` służy testom.

### 6.4 Dopasowanie czcionki (`fitDeck`)
- Jeden rozmiar na `fit_group` (całą pieśń), czyli najdłuższą zwrotkę.
- Ukryty kontener pomiarowy wewnątrz sceny (`visibility:hidden; position:absolute; contain: layout style`). Pomiar przez `scrollWidth`/`scrollHeight`, na które `transform` nie wpływa (w odróżnieniu od `getBoundingClientRect`).
- Wyszukiwanie binarne po całkowitych px w zakresie `[min, max]` z motywu. Kryterium: każdy slajd mieści się w obszarze bezpiecznym **bez łamania linii** (`white-space: pre`, linie z serwera). Dopiero gdy nie mieści się przy `min`, włączamy łamanie (`white-space: pre-wrap`).
- Wynik jest zapamiętywany pod kluczem `(fit_group, theme.hash, safeArea)`. Ekran dopasowuje z wyprzedzeniem `upcoming` w `requestIdleCallback`.

### 6.5 Identyczny podgląd
- Pilot używa **tych samych** komponentów `Stage` + `SlideView` + `fitDeck` z `@sursum/render`, z tym samym CSS, plikami czcionek i sceną 1920×1080. Różni się tylko zewnętrzne `scale()`, które nie zmienia układu.
- Wszystkie docelowe przeglądarki (Chromium na Pi, Chrome na Androidzie, Chrome/Edge na Windows) używają silnika Blink, a polityka bez łamania linii eliminuje jedyne realne źródło różnic.
- Podgląd ma wyłączone przejścia. Czerń i logo pokazuje jako znaczek przy miniaturze, z treścią pod spodem przygaszoną.
- Gdyby testy wykazały rozbieżność rozmiaru między silnikami (furtka iPad, Firefox), dodamy `FitReport` z ekranu do serwera, a piloty przejmą rozmiar ekranu. Protokół zostawia na to miejsce, w MVP tego nie implementujemy.

### 6.6 Strefy wykluczenia: słup w Tulcach
**Problem.** Projektor rzuca obraz częściowo na ścianę, a częściowo na ciemny słup. Tekst na słupie jest nieczytelny, a przesunięcie projektora nie wchodzi w grę (montaż, konserwator zabytków).

**Rozwiązanie.** Każdy ekran ma **profil** opisujący, które części sceny 1920×1080 nadają się do treści. Serwer wylicza z niego prostokąt treści, a ekran dopasowuje tekst wyłącznie do tego prostokąta. Słup dostaje czarną maskę, więc nie świeci na nim nic: ani tekst, ani jasne tło.

```rust
/// Opis fizycznego ekranu: co z kadru 1920×1080 jest użyteczne dla wiernych.
struct ScreenProfile {
    safe_area: Insets,                 // margines na overscan, w % kadru
    exclusions: Vec<ExclusionZone>,    // np. słup; zwykle 0–2 strefy
}
struct ExclusionZone {
    name: String,                      // "słup lewy" — dla ludzi w panelu kalibracji
    rect: Rect,                        // w pikselach sceny (prostokąt osiowy)
    mask: MaskMode,                    // Black (domyślnie) | None (tylko omijaj tekstem)
}
/// Wynik wyliczony na serwerze i wysyłany ekranowi oraz pilotom.
struct ScreenLayout {
    content: Rect,                     // gdzie wolno rysować tekst i logo
    masks: Vec<Rect>,                  // czarne prostokąty nad wszystkim oprócz nakładki
}
```

**Algorytm (`sursum-core::layout`, czysta funkcja `content_region(&ScreenProfile) -> Rect`).**
1. Zacznij od obszaru bezpiecznego.
2. Weź współrzędne x i y wszystkich krawędzi stref leżących w tym obszarze (razem z krawędziami samego obszaru).
3. Rozważ każdy prostokąt rozpięty na tych współrzędnych, odrzuć te, które przecinają którąkolwiek strefę, i wybierz **największy pod względem pola** (przy remisie: bliższy środkowi kadru).

Przy 1–3 strefach to kilkadziesiąt kandydatów, więc wystarczy prosta, czytelna enumeracja bez sprytnych struktur danych. Słup przy krawędzi daje węższy, przesunięty obszar; słup pośrodku daje większą z dwóch stron. Wynik ma test jednostkowy dla każdego takiego przypadku i `proptest`: wynik nigdy nie przecina strefy i zawsze leży w obszarze bezpiecznym.

**Rysowanie.** `LayeredStage` dostaje `layout` z migawki:
- treść i dopasowanie czcionki (`fitDeck`) używają `layout.content` zamiast całego obszaru bezpiecznego (to jedyna zmiana w dopasowaniu: inny prostokąt docelowy);
- warstwa `masks` (czarne prostokąty) leży nad treścią i tłem, a pod nakładką czerni i logo; logo też trafia do `layout.content`;
- obrazy (ogłoszenia) domyślnie wpisują się w `layout.content`. Opcja per pozycja „pełny kadr” pozwala pokryć cały ekran, ale maska nadal zaciemnia słup.

**Kalibracja (panel administratora na pilocie, poza mszą).**
1. Przytrzymanie przycisku „Kalibracja ekranu” (rola admin) wyświetla na ekranie siatkę z numerami pól i krawędzią obszaru bezpiecznego.
2. Na miniaturze w pilocie operator przeciąga prostokąt strefy. Ekran pokazuje go na bieżąco jako czerwoną ramkę, więc osoba w kościele widzi, czy pokrywa słup.
3. „Zapisz” utrwala profil w `settings` (klucz `screen_profile`), a serwer rozsyła nowy `layout`.

Edycja jest też możliwa w `config.toml` dla instalatora. Profil jest częścią urządzenia, nie wspólnej bazy, więc eksport i scalanie go nie przenoszą. Gowarzewo ma pusty profil.

**Podgląd na pilocie** rysuje ten sam `layout`. Maski są tam półprzezroczyste i zakreskowane, żeby operator widział słup, a tekst leży dokładnie tam, gdzie na ekranie.

**Ograniczenia i rozszerzenia.** Prostokąty osiowe wystarczą, bo słup jest pionowym pasem, a projekcja odwzorowuje scenę liniowo. Gdyby kalibracja na miejscu pokazała ukośną krawędź (projektor pod kątem), dodamy `ExclusionZone` jako czworokąt z maską `clip-path: polygon()` i wpisanym prostokątem. Model i protokół są na to gotowe, ale w MVP tego nie robimy. Układ dwukolumnowy (tekst po obu stronach słupa) świadomie odrzucamy: zwrotka rozcięta słupem czyta się gorzej niż mniejszy tekst z jednej strony.

## 7. Pilot do obsługi jedną ręką

- **Widok „Na żywo”** (tablet poziomo i pionowo, PC):
  - u góry miniatura **bieżącego** (duża) i **następnego** slajdu;
  - pośrodku lista pozycji zestawu z numerami i chipy sekcji bieżącej pieśni („1”, „2”, „Ref.”, „Most”, …);
  - na dole strefa kciuka: ogromne **Dalej ▶** i **◀ Wstecz**, mniejsze ⏮/⏭ pieśń, **CZERŃ** (zawsze jedno dotknięcie, wyróżniony kolor, przełącznik), **LOGO**, **#** (klawiatura numeryczna: numer pozycji w zestawie, skok od razu po zatwierdzeniu);
  - układ lustrzany dla lewo- i praworęcznych w `devices.prefs_json`;
  - dotknięcie slajdu, chipu lub pozycji od razu wyświetla.
- **Ergonomia dotyku**: `touch-action: manipulation`, cele co najmniej 15 mm, natychmiastowa informacja wizualna (`:active` + krótkie podświetlenie po `CmdResult`), `navigator.vibrate` na Androidzie, ignorowanie powtórzonych dotknięć w ciągu 150 ms (konfigurowalne).
- **Operacje niszczące** (usunięcie pozycji, wyczyszczenie zestawu, usunięcie pieśni): przytrzymanie ok. 700 ms z pierścieniem postępu i dodatkowo toast „Usunięto — Cofnij” przez 10 s. Czerń i nawigacja nigdy nie wymagają potwierdzenia.
- **Wyszukiwanie**: jedno pole tekstowe obsługuje numer w śpiewniku, tytuł i fragment tekstu. Wyniki pojawiają się już przy pierwszym znaku, a każdy ma akcje „Dodaj na koniec”, „Dodaj po bieżącej” i **„Pokaż teraz”**.
- **Edycja zestawu na żywo**: przyciski ↑ ↓, „przenieś na pozycję N” i usuń (przytrzymanie). Przeciąganie można dodać później. Program na ekranie się nie zmienia.
- **Edytor pieśni** (priorytet użytkownika, wygodny na PC z klawiaturą):
  - pole tekstowe w formacie zgodnym z OpenSong (`[V1]`, `[C]`, `||`, linie `.` z akordami);
  - pola metadanych (tytuł, numer w śpiewniku, autor);
  - po lewej podgląd slajdów wyliczany **na serwerze** (`POST /api/songs/compile`, z opóźnieniem 300 ms) i rysowany przez `@sursum/render`;
  - skróty klawiszowe: Ctrl+S zapisuje, Ctrl+Enter zapisuje i dodaje do zestawu;
  - wklejenie zwykłego tekstu (zwrotki rozdzielone pustą linią) zamienia się w sekcje `[V1] [V2]…`, a operator koryguje wynik.

## 8. Wyszukiwanie bez względu na polskie znaki

- `normalize(s)`: NFKD → usunięcie znaków kategorii Mn → małe litery → **jawna tabela** `ł→l, Ł→l, đ→d, ø→o, ß→ss, æ→ae, œ→oe, ı→i, ħ→h, þ→th, ŀ→l` → zwinięcie spacji i interpunkcji. Funkcja jest w core i testowana dla każdej polskiej litery.
- Indeks w pamięci: dla każdej pieśni znormalizowany tytuł z aka, pierwsza linia, wpisy śpiewnika i pełny tekst. Kilka tysięcy pieśni po ok. 2 KB to kilka MB, więc skan po każdym naciśnięciu klawisza jest szybki także na Pi 5. Indeks jest przebudowywany przyrostowo po zmianie pieśni.
- Ranking: dokładny numer w śpiewniku > prefiks tytułu > prefiks słowa w tytule > pierwsza linia > fraza w tekście > wszystkie słowa w dowolnym miejscu (AND, prefiksy słów). Remis rozstrzyga ostatnie użycie w zestawach.
- Kryterium wydajności: p95 poniżej 30 ms na Pi 5 przy 5000 pieśni, mierzone benchmarkiem w M2.

## 9. Import z OpenSong

- **Wejście**: CLI `sursum-server import-opensong <katalog>` oraz w przeglądarce upload ZIP-a całego katalogu OpenSong (dla PC z Windows: „spakuj folder OpenSong i przeciągnij”).
- **Pieśni**: `Songs/**` (pliki bez rozszerzenia, nazwa = tytuł, podfoldery → słowo kluczowe lub kategoria).
  - Odporny parser: BOM, CRLF, `&#13;`, deklarowane kodowania (dekodowanie przez feature `encoding` w quick-xml ⚠), nieznane elementy trafiają do `extra`.
  - Element w specyfikacji to `<timesig>`; obsługujemy też `time_sig` spotykane w plikach.
- **Konwencje tekstu**:
  - potwierdzone na opensong.org: spacja na początku linii tekstu, `.` akordy, `[V] [1-9] [C] [B] [P] [T]` i nazwy własne, `||` jako wymuszony podział slajdu;
  - ⚠ do potwierdzenia w M2 w pomocy programu i w repozytorium OpenSong (czytamy dokumentację, nie kopiujemy kodu; repozytorium jest na GPL): `;` jako komentarz, numerowane linie `1`, `2` w bloku `[V]` rozwijane do V1 i V2 ze wspólną linią akordów, `|` jako podział linii, `---`, `_`, `-`.
  - Każda reguła dostaje syntetyczny fixture i test. Weryfikację uzupełnia test na prawdziwej bibliotece parafii, uruchamiany lokalnie przez `SURSUM_REAL_LIBRARY=… cargo test -- --ignored`. Biblioteka nigdy nie trafia do repozytorium; test sprawdza tylko statystyki i brak błędów, bez zrzutów treści.
- **Zestawy**: `Sets/*`, `slide_group type=song` (`name` + `path` → dopasowanie do zaimportowanej pieśni, `presentation` → `order_override`), `custom` → `Text`, `scripture` → `Scripture`, `image` → `Image` (obrazy zapisane w zestawie trafiają do `assets`) ⚠ dokładna struktura grup image i style do sprawdzenia na przykładowych plikach.
- **Raport importu** (`import_runs.report_json`): liczby zaimportowanych, pominiętych i zduplikowanych pozycji (dopasowanie po `content_hash` i tytule), ostrzeżenia z ścieżką i linią, brakujące pieśni w zestawach. Ponowny import tej samej biblioteki jest idempotentny: aktualizuje pieśni o tym samym `source`, nie tworzy duplikatów.

## 10. Wspólna baza: eksport/import ze scalaniem (M3)
- **Paczka** `*.sursum` (ZIP): `manifest.json` (wersja formatu, `device_id`, `exported_rev`), `songs.jsonl` (pieśń + `revision` + `content_hash` + lista hashy przodków z `song_history`), `sets.jsonl` opcjonalnie, `songbooks.json`, `assets/`. Paczka służy też jako kopia zapasowa. Pobranie i przesłanie odbywa się w przeglądarce PC albo tabletu.
- **Scalanie** po `SongId`, z kroku na sucho (dry-run) z podglądem przed zatwierdzeniem:
  - ten sam hash → bez zmian;
  - hash przychodzący jest przodkiem lokalnego → zostaje lokalna;
  - lokalny jest przodkiem przychodzącego → przewinięcie do przychodzącej wersji;
  - inaczej → **konflikt**: zachowaj obie wersje (druga jako „kopia z Gowarzewa”) i oznacz do ręcznego rozstrzygnięcia;
  - miękkie usunięcia propagują się tak samo.
- Automatyczna synchronizacja przez internet: później. Format paczki i hashe przodków już ją umożliwiają.

## 11. Urządzenie, bezpieczeństwo i HTTPS

### 11.1 Dostęp i parowanie
- Serwer nasłuchuje na `0.0.0.0:80` (port w konfiguracji) i **odrzuca adresy źródłowe spoza** loopback, RFC1918, link-local i ULA (`ConnectInfo`). Na Pi dochodzi do tego reguła nftables.
- Sprawdzanie nagłówka `Host` (ochrona przed DNS rebinding) i **`Origin` przy upgradzie WS** (przeglądarki wysyłają ciasteczka przy upgradzie WS z obcego pochodzenia, więc to obrona przed CSWSH).
- Parowanie pilota: PIN administratora (ustawiony przy instalacji, przechowywany jako hash argon2). Po poprawnym PIN-ie serwer zapisuje urządzenie i ustawia ciasteczko `HttpOnly; SameSite=Strict` z losowym tokenem (256 bitów, w bazie tylko hash). Limit prób: wykładniczy backoff per IP. Lista urządzeń z możliwością odwołania w ustawieniach.
- Role: `screen` (tylko odczyt, bez autoryzacji), `operator` (nawigacja, zestawy, edycja pieśni), `admin` (import, scalanie, ustawienia, PIN; wymaga ponownego podania PIN-u administratora).

### 11.2 HTTPS (bezpieczny kontekst): rekomendacja
Bezpiecznego kontekstu wymagają Service Worker, instalacja PWA i Screen Wake Lock (Web MIDI odpada razem z MIDI). Zwykłe WebSockety `ws://`, zdarzenia klawiatury (pedał), przełączanie pełnego ekranu i wibracja działają bez HTTPS. Na PC z Windows wake lock nie ma znaczenia, a w pilotażu, gdy serwer działa na tym samym PC, `http://localhost` i tak jest bezpiecznym kontekstem.

### 11.3 Kiosk na Pi (Raspberry Pi OS Lite 64-bit, Trixie, wydanie 2026-10-06)
- Pakiety: `cage` (0.2.0 w Trixie), `chromium` ⚠ (nazwa pakietu i wariant od Raspberry Pi do potwierdzenia), `seatd` lub logind, `avahi-daemon`, `nftables`.
- `sursum-kiosk.service`: `User=kiosk`, `PAMName=login`, `TTYPath=/dev/tty1`, `StandardInput=tty`, `Conflicts=getty@tty1.service`, `After=sursum.service systemd-user-sessions.service`, `Restart=always`, `RestartSec=1`.
  - Polecenie: `ExecStart=/usr/bin/cage -- chromium --kiosk --noerrdialogs --disable-session-crashed-bubble --hide-crash-restore-bubble --incognito --no-first-run --disable-features=Translate --disable-pinch --overscroll-history-navigation=0 --check-for-update-interval=31536000 --password-store=basic --user-data-dir=/run/sursum-kiosk http://localhost/screen` ⚠ (aktualność każdej flagi i `--ozone-platform=wayland` sprawdzić na Chromium z Trixie w spike'u M1).
- Kursor: CSS `cursor:none` i brak urządzenia wskazującego ⚠ (zachowanie cage do sprawdzenia).
- Brak białego błysku: czarne tło w `<head>` jest wymagane. Dodatkowo sprawdzamy ⚠ pierwszą klatkę Chromium przed załadowaniem strony; jeśli bywa biała, kiosk startuje dopiero po `GET /healthz` serwera.
- Strażnik ekranu: serwer śledzi połączenie `/ws/screen`. Jeśli ekran nie połączy się ponownie w ciągu 5 s (np. awaria renderera ze „smutną kartą”), wykonuje `systemctl restart sursum-kiosk` (reguła polkit tylko dla tej jednostki). Restart kiosku codziennie o 3:00 przez timer.

### 11.4 HDMI, cichy start
- `cmdline.txt`: `video=HDMI-A-1:1920x1080@60D quiet loglevel=0 logo.nologo vt.global_cursor_default=0 consoleblank=0 console=tty3`.
- `config.txt`: `disable_splash=1`.
- Plan awaryjny dla przedłużaczy i projektorów z dziwnym EDID: `drm.edid_firmware=HDMI-A-1:edid/sursum-1080p.bin` z gotowym plikiem EDID w `deploy/pi/edid/` ⚠.
- Test akceptacyjny: Pi startuje przy wyłączonym projektorze, projektor włączony po 10 minutach pokazuje 1080p bez zmiany trybu, a odłączenie i podłączenie HDMI nie zmienia rozdzielczości.

### 11.5 Odporność na odcięcie prądu
- Root tylko do odczytu: raspi-config → Overlay File System (z partycją boot tylko do odczytu) ⚠ mechanizm do potwierdzenia na Trixie.
- **Osobna partycja `/data`** (ext4, `noatime`, domyślne `data=ordered`). Powstaje przez skrypt instalacyjny przed pierwszym rozszerzeniem rootfs albo przez zmniejszenie partycji (procedura w `docs/device-setup.md`). Na `/data` leżą:
  - `/data/sursum/{db, backups, assets, releases/<ver>/sursum-server, current -> releases/<ver>}` (aplikację można aktualizować przy roocie tylko do odczytu);
  - konfiguracja `/data/sursum/config.toml`.
- journald `Storage=volatile`. Watchdog: `RuntimeWatchdogSec=15` (sprzętowy) oraz `WatchdogSec=10` w `sursum.service` z `sd-notify`.
- Nośnik: karta A2 wysokiej wytrzymałości albo przemysłowa; opcjonalnie NVMe przez M.2 HAT+. Test tortur: 100 cykli odcięcia prądu sterowanym gniazdkiem, w trakcie przenikania i zapisu.

### 11.6 PoE
Nie ma oficjalnej nakładki PoE dla Pi 5. Są zgodne nakładki firm trzecich 802.3af/at z wyjściem 5 V/5 A: [Waveshare PoE HAT (H)](https://www.waveshare.com/product/raspberry-pi/boards-kits/poe-hat-h.htm) (mieści się w oficjalnej obudowie razem z Active Cooler), [(G)](https://www.pishop.us/product/power-over-ethernet-hat-g-for-raspberry-pi-5-5v-5a-output-802-3af-at) i [(J)](https://www.waveshare.com/product/poe-hat-j.htm), a także [52Pi P30](https://thepihut.com/collections/raspberry-pi-power-management-hats/products/52pi-poe-hat-for-raspberry-pi-5-4-3b), który potrzebuje co najmniej 30 W ze switcha. Do tego switch lub injector **PoE+ (802.3at)**.
Rekomendacja: PoE się opłaca, bo pod projektorem wystarczy wtedy jeden kabel. Istniejący kabel przedłużacza HDMI (Cat5e/6) po zdjęciu nadajnika i odbiornika służy jako łącze Ethernet+PoE, a Pi łączy się z projektorem krótkim kablem micro-HDMI–HDMI. Weryfikacja w M4 na jednym egzemplarzu: stabilność przy pełnym obciążeniu (Chromium + przenikanie) i brak komunikatów o niskim napięciu w `vcgencmd get_throttled`.

## 13. Środowisko deweloperskie, build, wdrożenie

### Kontener deweloperski
`.devcontainer/Containerfile` na bazie Debiana 13 (trixie):
- rustup (toolchain z `rust-toolchain.toml`), Node 26, `npm i -g pnpm@12`, zig + `cargo install cargo-zigbuild@0.24.1 cargo-nextest cargo-deny`, `just`;
- zależności Playwright przez `pnpm exec playwright install --with-deps chromium webkit` ⚠ (oficjalne wsparcie Playwright dla Debiana 13 do potwierdzenia; awaryjnie obraz Ubuntu 24.04).

Użycie:
- **Podstawowa platforma testów to Linux**: `just dev` na laptopie, ekran w Chromium (masz go nałożonego w systemie) w osobnym oknie `--app`/`--kiosk`, pilot w drugim oknie lub na tablecie. Playwright w kontenerze używa własnego Chromium, niezależnego od systemowego.
- **VS Code Dev Containers** (już zainstalowane na Aurora-DX) z Dockerem, który jest aktywowany socketem. Podman też zadziała; przy podmanie trzeba uważać na SELinux (`:Z`) i `--userns=keep-id`.
- Ten sam obraz można uruchomić jako distrobox do pracy w terminalu (`distrobox create --image localhost/sursum-dev`).
- System bazowy zostaje nietknięty. rustup i Node, które już masz w `$HOME` i Homebrew, nie są potrzebne w kontenerze, ale nie przeszkadzają.

### Polecenia (`justfile`)
- `just dev`: `cargo watch`/`bacon` serwera na :8080 i Vite dla `screen` i `remote` z proxy `/api` i `/ws` (`ws: true`) na :8080.
- `just build`: `pnpm -r build` → `cargo build --release -p sursum-server` (rust-embed wbudowuje `dist`).
- `just bindings`, `just test` (nextest + vitest), `just e2e` (Playwright uruchamia zbudowaną binarkę na losowym porcie z tymczasowym katalogiem danych).
- `just cross-pi`: `cargo zigbuild --release --target aarch64-unknown-linux-gnu.2.36` (glibc 2.36 działa i na Bookworm, i na Trixie 2.41; MIDI wypadło, więc nie potrzebujemy libasound i kompilacja krzyżowa jest prosta).
- `just cross-win`: `cargo zigbuild --target x86_64-pc-windows-gnu` ⚠. Źródłem prawdy dla wydań jest natywny runner Windows w CI.

### Wdrożenie i CI
- `just deploy <host>`: build → `scp` do `/data/sursum/releases/<ver>/` → atomowa zmiana linku `current` → `systemctl restart sursum` → sprawdzenie `GET /healthz` (do 20 s) → w razie błędu automatyczny powrót do poprzedniej wersji.
- CI (GitHub Actions, składnia zgodna z Forgejo Actions):
  - fmt, clippy `-D warnings`, nextest, kontrola dryfu bindingów ts-rs;
  - pnpm lint, typecheck (svelte-check), vitest, Playwright (chromium blokująco, firefox i webkit nieblokująco jako furtka dla Firefoksa na Linuksie i iPada);
  - artefakty aarch64-linux, x86_64-linux, x86_64-windows;
  - `cargo deny check licenses advisories` (tylko licencje permisywne, żeby nie zamykać żadnej opcji licencyjnej; żadnego kodu z FreeShow ani OpenSong).

## 15. Strategia testów

- **Rust, testy jednostkowe** (`sursum-core`, `sursum-formats`):
  - parser OpenSong: tabela przypadków brzegowych, m.in. brak `presentation`, odwołanie do nieistniejącej sekcji, duplikaty sekcji, numerowane linie z lukami, linie z samymi akordami, puste sekcje, `||` na początku, końcu i dwukrotnie, CRLF i BOM, nieznane elementy, deklarowane kodowanie windows-1250;
  - kompilator slajdów (limity linii, Forced/Optional, powtórzenia w order, klucze slajdów stabilne po edycji);
  - maszyna programu (granice, ghost, edycja na żywo, overlay, reguła Stale);
  - normalizacja (każda polska litera, wielkie litery) i ranking;
  - `content_region`: brak stref, słup z lewej, z prawej, pośrodku, dwie strefy, strefa poza obszarem bezpiecznym, strefa pokrywająca wszystko (wtedy błąd walidacji profilu zamiast pustego obszaru); `proptest`: wynik nigdy nie przecina strefy;
  - scalanie paczek (wszystkie gałęzie);
  - `proptest`: niezmienniki operacji na zestawie (pozycje ciągłe, brak duplikatów, nawigacja nigdy poza zakresem);
  - `insta`: migawki JSON typów protokołu (stabilność kształtu przewodowego).
- **Testy integracyjne protokołu** (`sursum-server/tests`, tokio-tungstenite):
  - serwer na porcie 0 z `tempfile`: Hello/Welcome/migawka, komendy, dwaj piloci (Stale), odrzucony `Origin`, brak ciasteczka, limit prób PIN-u;
  - restart serwera z tym samym katalogiem → pełne odtworzenie przy tym samym `boot_id`, logo przy symulowanym innym `boot_id` (wstrzykiwany `PlatformInfo`);
  - przerwanie procesu w trakcie zapisu (`abort()` w procesie potomnym) → baza otwiera się, `quick_check` ok.
- **Playwright** (`e2e/`, binarka + fixture'y PD, projekt `chromium` blokujący, `webkit` nieblokujący, emulacja tabletu):
  1. pierwsza klatka czarna: opóźnione ładowanie JS przez `page.route`, a kolor tła odczytany przed wykonaniem skryptu;
  2. Dalej na pilocie zmienia ekran (`data-slide-key`);
  3. **edycja zestawu nie zmienia ekranu**: dodanie, usunięcie i przeniesienie pozycji, usunięcie pozycji na żywo, edycja tekstu pieśni na żywo. Porównujemy `data-deck-id`, `data-slide-key`, zrzut ekranu i licznik `__sursum.transitions` przed i po;
  4. **po zerwaniu połączenia zostaje ostatni slajd**: zatrzymanie serwera → zrzut ekranu bez zmian i brak elementów błędu → wznowienie serwera → ponowne połączenie bez przenikania;
  5. restart przeglądarki (nowy kontekst) wraca do bieżącego slajdu;
  6. jeden rozmiar czcionki na wszystkich slajdach pieśni;
  7. podgląd na pilocie ma ten sam rozmiar czcionki i tę samą liczbę linii co ekran oraz zbliżony zrzut (porównanie z tolerancją po przeskalowaniu);
  8. czerń jednym dotknięciem, a nawigacja pod czernią nie odsłania treści;
  9. przytrzymanie przy usuwaniu (zwykłe dotknięcie nie usuwa) i działające „Cofnij”;
  10. mapowanie klawiszy pedału (`keyboard.press('PageDown')`) i ignorowanie `repeat`;
  11. dwa piloci widzą ten sam stan na żywo;
  12. **strefy wykluczenia**: dla profilu ze słupem prostokąt każdej linii tekstu (`getClientRects` przeliczone na współrzędne sceny) nie przecina strefy, piksele w strefie są czarne na zrzucie ekranu, a zmiana profilu przelicza rozmiar czcionki bez przeładowania strony.
- **Testy na urządzeniu (M4)**: tortura zasilania (100 cykli), test HDMI (projektor później, odłączanie), 8-godzinny test wytrzymałościowy (pamięć Chromium i serwera, brak wycieków), nagranie wyjścia HDMI grabberem ze startu i awarii.

## 21. Czy Chromium to najlepszy silnik wyświetlania na Pi?

**Rekomendacja: tak, Chromium pod cage zostaje silnikiem w MVP.** Strona ekranu pozostaje jednak niezależna od silnika, a w M1 i M4 robimy krótki pomiar porównawczy z WPE WebKit (cog).

| Kandydat (Debian Trixie) | Za | Przeciw |
|---|---|---|
| **Chromium** (150 w Trixie; Raspberry Pi utrzymuje też własny build z akceleracją) | **ten sam silnik Blink co wszystkie piloty** (Chrome na Androidzie, Chromium na Linuksie, Edge na Windows), więc podgląd jest identyczny bez dodatkowej pracy; oficjalnie wspierany i akcelerowany przez Raspberry Pi; dojrzałe flagi kiosku; 4 GB RAM w pełni wystarcza | ciężki (kilkaset MB RAM, start kilka sekund); flagi kiosku zmieniają się między wersjami; ryzyko „smutnej karty” (obsłużone przez strażnika kiosku) |
| **WPE WebKit + cog** (wpewebkit 2.48.3, cog 0.18.4 w Trixie) | zaprojektowany do urządzeń wbudowanych; lżejszy, szybszy start; cog może rysować bezpośrednio na DRM/KMS bez cage; brak interfejsu przeglądarki, który mógłby się pokazać | **inny silnik niż piloty**, więc podgląd przestaje mieć gwarancję zgodności co do piksela; mniejsza społeczność i mniej doświadczeń na Pi 5; nowsze funkcje CSS i Web Animations pojawiają się później |
| Firefox ESR (140 w Trixie) w trybie kiosku | dobry silnik, dobre wsparcie Waylanda, konfiguracja kiosku przez `policies.json` | łączy wadę WPE (inny silnik niż piloty, więc brak gwarancji identycznego podglądu) z wadą Chromium (podobnie ciężki); Raspberry Pi optymalizuje przede wszystkim Chromium; ESR dostaje nowe funkcje z opóźnieniem |
| Natywny renderer w Ruście (wgpu, cosmic-text) | najszybszy start, pełna kontrola, żadnej przeglądarki na urządzeniu | łamie decyzję 3 i zasadę „nic dwa razy”: podgląd na pilocie musiałby używać tego samego renderera skompilowanego do WASM; wielokrotnie więcej pracy; tracimy CSS przy motywach |

Uzasadnienie: najważniejsze wymaganie, które silnik wpływa (identyczny podgląd), spełnia tylko Chromium, bo wszyscy wskazani klienci używają Blinka. Słabości Chromium (wielkość, flagi, awarie renderera) plan już ogranicza: strażnik kiosku, przypięta wersja, czarne tło w `<head>`, nagranie HDMI w testach.

Furtka, która kosztuje niewiele:
- strona ekranu używa wyłącznie standardowych API (Web Animations, `document.fonts`, `img.decode()`), bez funkcji dostępnych tylko w Chrome;
- jednostka systemd kiosku czyta polecenie silnika z `/data/sursum/kiosk.env`, więc zmiana silnika nie wymaga przebudowy;
- **spike porównawczy** (pół dnia w M1, powtórzony w M4) mierzy na Pi 5 czas od zasilania do pierwszej klatki, zużycie RAM po 8 h, płynność przenikania 1080p60, białą klatkę przy starcie i zachowanie po odłączeniu HDMI. Jeśli cog wyraźnie wygra na starcie i stabilności, a test podglądu (Playwright nr 7, projekt webkit) pokaże zgodność, wracamy do decyzji w ADR 0009.
